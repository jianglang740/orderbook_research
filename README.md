## 研究目的：

1. 在研究一个问题之前我们首先需要搞懂我们为什么要研究它，换言之就是我们研究它的意义是什么？在这之前我想说在最开始学习量化的时候绝大多数普通人应该都是这样的一个路径（包括我）：



- **⭐️⭐️⭐️脑子里有了一套策略，我称之为"想法/灵感"，然后想验证它能不能赚钱，于是就开始学习做回测，在这个阶段会遇到一系列问题，然后去尝试通过学习解决它们，验证通过之后就想着怎么才能把这个策略运用到实盘交易或模拟交易当中，然后又在这个过程中发现一系列问题；有人去学习并解决了这些问题走的更远，有人学到一半放弃了于是被甩在身后。**



- **⭐️⭐️⭐️这就是一个量化学习的最小路径闭环，我称之为“干中学”，边干边学，当然实际上的量化有着一套严谨的工程逻辑，就我目前的认知而言，我认为量化基本可以由【数学】+【代码】组成，其中数学部分概指线性代数、统计学习方法（机器学习实际上也是统计学），概率论等等，它负责策略的研究、优化、风控等等，属于量化投研部分；而代码部分泛指计算机技术，负责把“想法”落地，并用一系列技术栈构建一个严谨的工业化系统，属于量化开发部分。**


1. 在上述过程中大家一开始接触到的交易数据可能普遍是k线数据，并基于它手动做交易或学习简单的“双均线代码”、“布林带代码”、“马丁策略代码”等策略进行量化入门，而k线数据属于市场上的“宏观结构”，而本项目要研究的orderbook数据和tick trades数据属于市场上的“微观结构”，二者本质上都属于离散型时间序列数据，只是采样粒度不同，但却又有着巨大差别，学习和使用它们对所需要掌握的知识和技术栈、以及所使用的机器性能差别也不小；

2. 前者主要用于中低频量化交易，比如老生常谈的“市场只有两种状态——趋势和震荡”，并依据它做策略，而后者则主要用于高频领域的量化交易，注意高频与短线或超短线不一样，更依赖“少量多次”的积少成多思想，我在研究笔记里详细对比了这两种数据的差别，简而言之就是orderbook数据和tick trades数据的信息率更高、信息更灵敏、采样粒度更细，这也是它为什么适用于高频量化交易领域以及本项目研究它的原因。


## 研究结果：

**这是目前我的解决方案，并基于以下内容做了代码实现（代码实现分为用原始的rest+ws方法以及用ccxt pro两种方式）：**



- 利用Binance官方规定的WebSocket增量流数据更新消息中的三个ID字段（U、u、pu），配合REST快照数据返回的lastUpdateId，实现本地订单簿与交易所状态 严格一致，避免因为网络延迟、消息乱序或丢包而导致订单簿数据错误；简而言之就是用REST 全量快照 + WebSocket 增量更新，然后在本地内存维护一个多线程的队列，而不是用 WebSocket 全量快照；

- 具体来说，Binance 期货的深度增量流（<symbol>@depth）每条消息都包含：

```
U：本次更新的第一个事件 ID（起始 ID）

u：本次更新的最后一个事件 ID（结束 ID）

pu：前一条消息的最后一个事件 ID（用于衔接）

REST 快照返回的 lastUpdateId 代表该快照包含的最后一个事件 ID
```

- 基于这套规则，我们可以设计以下包含对齐、连续、更新的订单薄重建流程：

```
1. 订阅币安交易所的 WebSocket 增量流，开始缓存收到的消息（先不处理）
2. 用 REST 拉一份完整快照，记下 lastUpdateId = N 
3. 丢弃所有 u <= N 的缓存消息
4. 找到第一条满足 U <= N+1 <= u 的消息，从它开始处理
5. 此后每条消息：
     验证 pu == 上一条的 u（版本连续性）
     遍历 bids/asks 差量：qty=0 删除，qty>0 新增或覆盖
6. 如果发现版本号不连续，重新走步骤 1-4

更新规则：

qty = 0  → 删除该价格档位
qty > 0  → 新增或覆盖该价格档位的数量

```
